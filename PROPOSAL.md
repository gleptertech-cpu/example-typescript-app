# Proposal: Packaging and Deploying `example-typescript-app`

## TL;DR

Containerise it, run it on ECS Fargate behind an ALB, provisioned with Terraform, deployed via GitHub Actions using OIDC (no static AWS keys). Environment separation (dev/staging/prod) is done within a single AWS account for this exercise, not across three accounts — that's a deliberate scope cut, explained below, not an oversight.

## 1. How I'd package and deploy it

**Moving parts, end to end:**

1. **Container image** — a multi-stage `Dockerfile`: a build stage with the full `npm install` + `tsc` toolchain, and a slim runtime stage with only the compiled `dist/` output and `node:22-alpine`, running as a non-root user. No devDependencies, no source, no build tooling ship in the final image.
2. **Registry** — an ECR repository (`terraform/modules/ecr`), with `scan_on_push` enabled and immutable tags, so a tag can never silently point at a different image later.
3. **Compute** — ECS Fargate (`terraform/modules/ecs`): a cluster, a task definition (the container spec — image, port, env vars, logging), and a service (keeps the desired number of tasks running, handles rolling deploys).
4. **Networking & access** (`terraform/modules/alb`) — an Application Load Balancer in front of the service. The ALB's security group allows inbound HTTP from the internet; the task's security group (in the `ecs` module) only allows inbound traffic _from the ALB's security group_ — nothing can reach the container directly.
5. **IAM** (`terraform/modules/iam`) — an execution role (lets ECS pull the image and write logs) and a task role (what the running application itself can do via the AWS API — currently nothing, since the app calls no AWS services).
6. **CI, app** (`.github/workflows/ci.yml`) — on every PR, and on every push to a `feature/**`, `fix/**`, or `patch/**` branch: install, lint, format-check, build, build the Docker image.
7. **CI/CD, infrastructure** (`.github/workflows/terraform.yml`) — a separate pipeline, triggered only by changes under `terraform/**`: `fmt -check`/`validate` plus a per-environment `terraform plan` on PRs, and a per-environment `terraform apply` on merge to `main`. Uses its own, more-privileged OIDC role (`github-actions-example-typescript-app-terraform`) — separate from the app-deploy role below, since applying Terraform needs to create/modify IAM roles, security groups, and the ALB, not just update a running ECS service.

   Both this and the app pipelines ignore each other's path (`ci.yml`/the deploy workflows use `paths-ignore: terraform/**`; `terraform.yml` uses `paths: terraform/**`), so an app-only change never re-plans or re-applies infrastructure, and a pure infra change never rebuilds or redeploys the app image.
8. **CD, dev & staging** (`.github/workflows/deploy-non-prod.yml`) — on every push to `feature/**`, `fix/**`, `patch/**`: build and push the image (tagged with the commit SHA) to both the `dev` and `staging` ECR repos, then deploy to both environments' ECS services in parallel (a matrix job). This gives fast feedback in a real running environment before a PR even exists, not just local testing.
9. **CD, production** (`.github/workflows/deploy-prod.yml`) — on merge to `main` **only**: build and push to the `prod` ECR repo, render a new task definition, deploy. Production never deploys from a feature branch directly — only from a merge to `main`, i.e. an actual reviewed PR. Both CD workflows authenticate via **OIDC role assumption**, not static `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` secrets.

The Terraform is split into one module per service (`terraform/modules/ecr`, `iam`, `alb`, `ecs`), composed by a root `main.tf` that looks up the default VPC once and wires each module's outputs into the next module's inputs, rather than one large file mixing every resource type together.

**Same repo, separate pipelines, for this exercise — a separate repo would be the better long-term answer.** `terraform.yml` and the app workflows are already path-scoped so they never trigger each other (covered above), which gets most of the practical benefit of separation without needing a second repo for a one-hour exercise on one small app. But it's not the cleanest version of this: a genuinely separate "infra" repo would also give infra its own access control (who can approve infra PRs doesn't have to be the same list as who can approve app PRs), its own versioning/release cadence independent of app releases, and would stop an application engineer's routine PR from even *showing* infra changes as a navigable option, rather than just one more folder to accidentally touch. I didn't split it into two repos here because doing so for a single trivial app would be more process overhead than the thing it's protecting — but for a real, growing system with its own platform/infra owners distinct from the people shipping app features, I'd actually recommend it as the default, not the exception.

**State** — the main config stores its state remotely in S3 (`terraform/terraform.tf`'s `backend "s3"` block), not locally. That bucket is created by a separate `terraform/bootstrap` config, run once, by itself, with local state — it can't use the backend it's creating on a first run, which is the usual chicken-and-egg problem with this pattern. `terraform/bootstrap/README.md` has the run order.

**Environments are Terraform workspaces, not a variable.** `dev`/`staging`/`prod` are three separate workspaces against the same backend, each with fully isolated state (the S3 backend automatically prefixes the configured key with `env:/<workspace>/`). `main.tf` derives `environment` from `terraform.workspace` via a map lookup — an unexpected workspace name fails immediately with Terraform's own "invalid index" error, rather than silently creating a wrongly-named set of resources. I actually ran this: created all three workspaces, applied against a throwaway local-backend copy of the same lookup logic to confirm each resolves correctly, and confirmed the `default` workspace fails exactly as designed. This replaces an earlier version of this config that passed `environment` as a plain variable with a fixed backend key — which, on reflection, had a real latent bug: every environment would have written to the *same* state file, since nothing was actually namespacing the state itself, only the resource names inside it.

**What a deploy looks like, concretely:** merge to `main` → CI has already proven the image builds and the Terraform is valid → CD builds and pushes the real image → a new task definition revision is registered → ECS starts new tasks on that revision → the ALB only sends traffic to tasks that pass the `/health` check → once the new tasks are healthy, old ones are drained and stopped. If the new tasks never pass health checks, **ECS's deployment circuit breaker rolls back automatically** (configured in `main.tf`) — that's the rollback path, without anyone needing to notice and intervene manually.

## 2. What else I'd change, in priority order

1. **Health endpoint, structured logs, graceful shutdown (done first, done already).** These were zero-cost to add and unlock everything else — you can't have a sane rollback path or a load balancer without something to check, and ECS sends `SIGTERM` on every deploy/scale-in, so without handling it, in-flight requests get cut off on every single deploy, not just failures.
2. **Config through the environment (done).** Already reads `PORT`; I added `NODE_ENV` via the task definition rather than hardcoding it anywhere.
3. **Lint and format checks in CI (done).** Added ESLint and Prettier, both actually run (`npm run lint`, `npm run format:check` in both `ci.yml` and `deploy-non-prod.yml`), not just configured. Worth naming the actual reason I added this: while working on this exercise, my editor auto-formatted `src/index.ts` with a trailing comma Prettier's defaults don't match out of the box — a small drift that's easy to not notice until it shows up as unexplained diff noise in a future PR. A `format:check` step catches exactly that class of thing automatically, rather than relying on everyone's editor agreeing by coincidence.
4. **A test suite (not done — named gap).** There are zero tests, same as before this exercise. I'd add this next, before anything below — right now CI "passing" only proves the code compiles and lints clean, not that it works. I'd start with one test hitting `/` and `/health` and build out from there.
5. **Terraform tests (not done — named gap, separate from the app test suite above).** `terraform.yml` runs `fmt`/`validate` and `plan`, but nothing exercises the module logic itself — the kind of thing a `*.tftest.hcl` file with Terraform's native test framework and `mock_provider "aws" {}` would catch (e.g. "does the task security group really only allow traffic from the ALB's security group," "does the ECS service actually get `deployment_circuit_breaker.rollback = true`"), without needing real AWS credentials or costing anything to run. This is a different kind of test from the app's own test suite above — one checks the application behaves correctly, this would check the *infrastructure definition* is actually shaped the way I claim it is, catching a regression in `terraform/modules/*` before it ever reaches a real `plan`/`apply`.
6. **Security and dependency scanning (sketched as named placeholders, not wired up — see `ci.yml`'s `security` job).** I added the gates I'd actually use, each a `TODO` rather than fully configured, since each needs an account/token this exercise doesn't have: SonarQube (SAST — bugs and security flaws in the code I wrote), Bearer (data-flow-focused scanning — where sensitive data goes and whether it's handled safely), Snyk (SCA — known CVEs in dependencies), and Checkov (IaC scanning — misconfigurations in the Terraform itself, e.g. a security group open wider than it should be). This is standard practice from my own production experience, not a generic checklist — I'd prioritise Checkov and Snyk first (they need no code changes to start catching real issues), SonarQube and Bearer next once there's actual application logic worth scanning beyond a hello-world handler.
7. **Custom VPC with private subnets (not done — named gap).** This Terraform uses the account's **default VPC**, with the Fargate tasks getting public IPs directly. That's a real compromise for a one-hour exercise on a trivial app — I wouldn't ship this exact setup for anything handling real traffic or data. The correct version: tasks in private subnets, only the ALB in public ones, egress via a NAT gateway. I cut this specifically because building a VPC from scratch (subnets, route tables, NAT, IGW) would have consumed most of the hour on networking plumbing rather than the actual deploy story.
8. **The one-time IAM OIDC roles (not done — named gap).** All three deploy/infra workflows assume an IAM role already exists with a trust policy scoped to this repo's GitHub OIDC provider — and deliberately **two different roles**: `github-actions-example-typescript-app` (narrow - just ECR push and ECS service updates, used by `deploy-prod.yml`/`deploy-non-prod.yml`) and `github-actions-example-typescript-app-terraform` (broader - can create/modify IAM roles, security groups, the ALB, etc., used only by `terraform.yml`). Neither role is created anywhere in this repo - `terraform/modules/iam/` only creates the two *ECS* roles (execution role, task role), which are a completely different thing used by AWS services at runtime, not by GitHub Actions to authenticate into AWS in the first place. Bootstrapping these needs two things, typically done once per AWS account: an OIDC identity provider registered in IAM trusting `token.actions.githubusercontent.com` (shared account-wide, not per-repo), and the roles themselves with trust policies scoped to this specific repo. I deliberately left this out of the app-level Terraform here, rather than have an app module provision the very account-level trust relationship its own pipeline depends on to run - it's a real missing piece before any of these pipelines would actually work, same category of gap as `terraform/bootstrap`'s state bucket.
9. **Required review before merge (half done — `.github/CODEOWNERS` added, branch protection itself not configured).** A PR review requirement is a repo *setting*, not something a workflow file can enforce on its own — `CODEOWNERS` only takes effect once branch protection on `main` is turned on with "Require a pull request before merging," "Require approvals," and "Require review from Code Owners" checked, plus "Require status checks to pass" pointing at `ci.yml`'s `build-and-test` job. I didn't configure this for real: it's a one-time GitHub repo-settings change, not something a Terraform run or a workflow file applies, so it's a manual step I'm leaving named here rather than clicking through myself on a repo about to be handed over for review. `CODEOWNERS` is set to my own GitHub username (`@gleptertech-cpu`) as the placeholder reviewer.
10. **Dependency management (sketched — `.github/dependabot.yml`).** `package-lock.json` was already committed before this exercise (good) — I added a Dependabot config covering all three ecosystems actually in this repo: npm (the app's dependencies), GitHub Actions (the `actions/*`/`aws-actions/*` versions pinned in the workflows), and Terraform (provider versions). Weekly, capped at 5 open PRs for npm so it doesn't flood the repo. This overlaps with Snyk above but isn't redundant with it — Dependabot keeps things current proactively (opens a PR the moment a newer version exists), Snyk catches what's already vulnerable regardless of how current it is. Unlike the security-scanning placeholders, this one needs no tokens/accounts — it's genuinely ready to work as soon as it's merged, Dependabot is built into GitHub itself.
11. **Observability beyond logs (explicitly out of scope per the brief, mentioning only).** Logs go to CloudWatch via `awslogs` already. Dashboards and alerting are called out as out of scope for this exercise — I'd want basic alarms on ALB 5xx rate and unhealthy target count before calling this production-ready, but that's genuinely a "next" item, not something to sketch here.
12. **Beyond this app: a reusable CI/CD template, if one doesn't already exist.** Everything built here — lint/format checks, the security-scanning gates, a generic smoke test, and genuine 3-account dev/staging/prod deployment — is exactly the kind of thing a new app shouldn't have to rebuild from scratch every time. A bare-minimum, hardened starter template (a GitHub Actions reusable workflow, or an organisation-level workflow template) that already wires up linting/Prettier, the security scanners as real gates rather than placeholders, a baseline smoke test, and genuine per-account OIDC roles for dev/staging/prod would make a new service's CI/CD setup minutes of configuration instead of hours of reassembling the same pieces — and it means security/scanning is the default a team starts with, not something bolted on later once there's already a backlog of findings to catch up on. Worth raising as a team-level investment regardless of what happens with this specific app.

## 3. Reasoning — what I considered and rejected

- **ECS Fargate vs. EC2 vs. Lambda vs. App Runner.** No persistent state, no host-level customisation needed, so Fargate removes the host-management burden EC2 would add for no benefit here. Lambda (behind API Gateway) would also work for a trivial app like this and might even be a faster path to "deployed" — I didn't pick it because it's a less natural fit for a long-running HTTP server pattern the team will likely grow into something heavier than hello-world, and Fargate's operational model (tasks, services, rolling deploys) is the one most directly reusable as the app grows. App Runner is genuinely a reasonable lighter-weight alternative to hand-rolling ECS+ALB — I went with ECS Fargate specifically because it's the tool I have the deepest real production experience with, and it gives the team something they can extend (add a second service, add autoscaling policies, etc.) rather than a more opinionated managed black box.
- **Worth naming directly: if this were a real single-page application (static HTML/CSS/JS, no server-side logic) rather than a server process, I would not reach for a container at all.** The right call for a genuine static SPA is S3 + CloudFront — no server to patch or scale, pennies to run, and CloudFront gives you HTTPS and edge caching for free. This repo's app is a small Node.js HTTP server, not static content, so that option was never actually on the table here — but I'm choosing ECS Fargate in this proposal specifically to demonstrate container packaging and orchestration, which is what this exercise is evaluating, not because every web application should default to a container. Using the heavier tool because it's the one being tested, while being clear that it isn't always the right one, is itself the judgement call worth stating plainly rather than leaving implicit.
- **Terraform vs. CDK vs. manually clicking it together.** Terraform because it's explicitly what I'm strongest in and the brief says tooling choice doesn't matter, reasoning does. Manually clicking it together in the console was never a serious option — "repeatably" is in the brief's own first question, and console changes aren't repeatable or reviewable.
- **Default VPC vs. a custom one.** Covered above — a real, named scope cut for the one-hour budget, not a default I'd actually recommend keeping.
- **Single AWS account vs. three (dev/staging/prod).** I considered this and deliberately didn't build it. Separate accounts per environment is the right call for a real production system — blast-radius isolation, separate IAM boundaries, separate billing. But standing up multi-account infrastructure (account vending, cross-account trust roles, per-account state) is substantial work on its own, and attempting it for real inside a one-hour exercise on a hello-world app would have meant not getting to the actual deploy story, the health check, or the rollback path at all. Here, environment separation is done via a Terraform `environment` variable that namespaces resource names within one account. I'd revisit this the moment there's real data or real users involved.
- **GitHub Actions vs. another CI tool.** No strong opinion either way; GitHub Actions because the repo's already on GitHub and it avoids standing up anything extra.
- **OIDC vs. static AWS credentials in CI.** Static access keys as GitHub secrets are the common shortcut, but they're long-lived and have to be manually rotated. OIDC role assumption gives short-lived, automatically-expiring credentials scoped to this specific repo, for roughly the same setup effort — worth doing from day one rather than retrofitting later.

## 4. Honesty about gaps

- **The Docker build is actually verified, not just written.** I built the image for real (`docker build`), ran it, confirmed `/` and `/health` both respond correctly, confirmed the process runs as the non-root `app` user (not root), and confirmed graceful shutdown works — stopping the container logs `Received SIGTERM, shutting down` → `Closed out remaining connections` before it exits, rather than being killed mid-request.
- **I didn't apply the Terraform** — no AWS credentials configured in this environment. `terraform validate` passes across the full module tree (root + all four modules) and the resource graph is internally consistent, but it's never been run against real AWS. I'd expect a few small fixes on a first real `apply` (IAM policy ARNs, subnet/AZ availability for Fargate in the target region) that only surface at apply time.
- **The IAM OIDC trust role is referenced but not created** — see item 6 above.
- **No tests exist** — named directly above as the actual next priority, not quietly skipped.
- **The security scanning steps in `ci.yml`'s `security` job are named placeholders, not real gates** — each is a `TODO` with the specific action/tool named, not an actual integration. They need accounts/tokens (`SONAR_TOKEN`, `SNYK_TOKEN`, a Bearer setup) this exercise doesn't have. The point of including them was to show the shape of the pipeline I'd build, not to claim they're enforcing anything yet.
- **`deploy-non-prod.yml` and `deploy-prod.yml` both assume the environment's infrastructure already exists.** Neither workflow runs `terraform apply` — they only build/push an image and update an already-running ECS service. Someone has to have already run the Terraform once per environment (`terraform workspace select dev && terraform apply`, then `staging`, then `prod`) to create each one's cluster/service/ECR repo before these pipelines have anything to deploy to. I kept infrastructure provisioning and application deployment as separate concerns deliberately (changing app code shouldn't require a Terraform apply, and vice versa), but it's worth being explicit that "push to a feature branch" only works once dev and staging actually exist.
- **AI assistance:** I used Claude Code throughout this exercise — drafting the health-endpoint/graceful-shutdown code, the Dockerfile, the Terraform, and the CI/CD workflows, and talking through the sequencing and tradeoffs with it as I went. I reviewed and reasoned through each piece myself rather than taking it uncritically (e.g. correcting an initial instinct toward a three-AWS-account setup, given the one-hour budget).
